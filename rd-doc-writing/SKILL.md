# RD Doc Writing

Source: Feishu doc `文档的艺术：研发工程师怎么写好文档` (`MWlKdSqOyol1zPxgGy6cNlVTn4b`).

Keep this skill faithful to that source. Do not add domain examples that are not in the source doc unless the user provides them.

## 适用文档

原文把研发工程师的文档分成两类工作方式：

- **开发**：完成产品需求、技术需求时写设计文档；进行某些操作时沉淀 SOP 类文档。
- **研究**：调研新技术或竞品时写调研文档；确定项目可行性、难点、方案设计时写项目文档；技术交流时写技术分享文档。

文档对研发很重要：

- 对个人：提升沟通效率，减少重复沟通；提升表达、沟通和分析能力。
- 对团队：沉淀经验、帮助成员快速找到信息和资源、减少重复劳动。

## 核心：想清楚文档目的

写文档前先想清楚：这个文档要达到什么目的？

原文例子：

- **SOP 文档**：方便自己或组员后续快速执行，不用从头调研和踩坑。目的偏知识分享、经验沉淀。
- **项目立项文档**：让项目组成员清楚要做什么、为什么做、收益是什么、如何执行、里程碑是什么、风险如何管理。目的偏项目执行和落地。
- **述职答辩文档**：让评委清楚背景、问题、难点、分析拆解、解决方案、项目收益、未来规划和个人思考。目的偏证明解决问题能力和规划能力。

最重要的是：文档是给读者看的，要让读者看懂你想表达的意思。

## 表达逻辑：金字塔原理

原文推荐两个方法：

1. 自上而下表达，结论先行。
2. 自下而上思考，总结概括。

### 自上而下表达

按原文步骤组织：

1. **画出主题方框**：确定文章要讨论的主题。
2. **设想主要疑问，确定读者**：文章面对哪些对象？希望回答读者关于该主题的哪些疑问？
3. **写出对该疑问的回答**：如果不清楚答案，先注明有能力回答该疑问。
4. **说明背景**：把主题与背景结合，写出读者不会有争议的事实。
5. **指出冲突**：背景中发生了什么问题、意外、变化，让读者产生疑问？
6. **检查主要疑问和答案**：背景与冲突是否能自然引出主要疑问？答案是否对得上？

目的：确保写作者知道自己要回答哪些疑问。

### 自下而上思考

当主题、读者疑问或读者认知不清楚时，从关键句层次开始：

1. 列出想表达的所有思想要点。
2. 找出各要点之间的逻辑关系。
3. 得出结论。

## 技巧：写好序言

序言是文档与读者建立沟通的重要部分。

常见问题：背景介绍太潦草，没有引入主题和冲突，很快进入方案设计，导致读者不理解背景和问题。

原文建议序言采用讲故事形式：

1. 介绍读者熟悉的 **背景**。
2. 说明发生的 **冲突**。
3. 由冲突引发读者的 **疑问**。
4. 针对疑问给出 **答案**。

重点：

- 引发读者疑问很重要，让读者带着疑问和思考去读。
- 序言要激发读者兴趣，让读者专注话题。

## 关键点：推导出方案

原文指出一个常见问题：刚交代完背景，马上进入方案设计。

这会带来两个问题：

- 读者会问：为什么是这个方案？怎么得出这个结论？
- 缺少支撑方案必要性和合理性的推导，不利于方案推进。

推荐做法：

1. 用序言铺垫：背景是什么，冲突点是什么，文章主题是什么。
2. 加入问题分析：拆解问题，把大问题拆成小问题；说明解决难点；推导解决思路和切入点，为方案做铺垫。
3. 承接上文引出解决方案：方案要和问题拆解一一对应；如果有多个方案，说明哪个更好。
4. 总结效果和收益：说明做出来的效果、收益，并尽量用数据佐证。

好处：

- 方案自洽，由层层推理得出。
- 读者能顺着思路深入，并一起思考方案。

## 技巧：学会画图

一图胜千言，前提是图有内容，不是胡乱画图。

图的作用：

- 简化复杂信息。
- 增强可读性。
- 提高沟通效率。

研发工作中常见的图：

- **流程图**：展示工作流程或数据流，适合描述系统架构、算法步骤等。
- **架构图**：展示系统组件及关系，适合描述软件架构和设计模式。
- **示例图**：具象化展示描述，或展示示例代码执行结果、数据结构。

画图技巧：

- 想清楚表达重点是什么，为关键部分添加注释。
- 清晰简洁，风格一致，避免不必要的细节和装饰。
- 善用模板，飞书画板模板已经能覆盖很多日常场景。

## 关键点：数据佐证

数据能增强文档可信度和说服力。

数据的作用：

- **客观性**：为观点提供事实基础。
- **证据支持**：让读者更容易接受结论。
- **详细分析**：帮助读者更全面理解问题，为决策提供依据。

使用数据时要注意：

- 数据必须靠谱，经得起推敲。
- 不要为了证明观点而找数据。
- 尽量保持公正心看待结果。
- 写在文档上的数据，要知道来源和计算方法。
- 不要拿自己都不知道来源和算法的数据去讲。

## 提升文档能力

原文建议：

- 多看好的文档，学习高手，模仿优秀表达。
- 认真写好每一篇文档，每一篇认真写的文档都是积累。
- 重在积累，文档写多后回看以前的文档，会知道如何改进。
- 多读书、多写、刻意练习。

## Companion Review

When using this skill, also review the draft with `technical-doc-writing` if the document needs to drive alignment or decisions.

Use this skill to check:

- 目的是否清楚。
- 序言是否有背景、冲突、疑问、答案。
- 方案是否从问题推导出来。
- 图是否帮助表达重点。
- 数据是否有来源和计算方法。

Use `technical-doc-writing` to check:

- 为什么写、谁看、为什么看是否清楚。
- 标题是否表达观点。
- 框架是否围绕业务逻辑和核心指标。
- 是否有决策点、决策角色、可选项或推动动作。
- 是否有数据和用研偏差。

## Checklist

- [ ] 文档目的明确，不只是为了记录。
- [ ] 读者是谁、读者疑问是什么已经明确。
- [ ] 序言有背景、冲突、疑问、答案。
- [ ] 没有从背景直接跳到方案。
- [ ] 问题有拆解，大问题拆成小问题。
- [ ] 方案和问题拆解能对应上。
- [ ] 如果有多个方案，说明了哪个更好。
- [ ] 总结了效果和收益。
- [ ] 关键收益尽量有数据佐证。
- [ ] 数据来源和计算方法清楚。
- [ ] 图有明确表达重点，不是装饰。
- [ ] 文档经过自上而下表达和自下而上检查。
