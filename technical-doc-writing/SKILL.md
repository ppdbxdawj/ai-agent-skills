# Technical Doc Writing

Source: Feishu doc `如何写文档v2` (`UZDqdFn6PoHogRxnapSczr1tnv8`).

This skill should stay faithful to that source. Do not add domain examples that are not in the source doc unless the user provides the current document context.

Companion skill: use `rd-doc-writing` as a second-pass reviewer when the document is an RD design doc, SOP, research doc, project doc, technical sharing doc, or promotion/defense doc. Keep this skill focused on `如何写文档v2`: 预期/目标、受众视角、观点标题、逻辑拆解、判断力、推动决策、双周报、业务关键问题材料。

## 写在前面

写文档前，先对齐预期和目标，拷问自己三次：

1. 为什么要做这件事？
2. 谁想看？
3. 为什么要看？

写文档中，关注四个关键要素：

- **视角 / 受众**：要说什么。
- **框架**：怎么说清楚。
- **判断力**：怎么让人信服。
- **决策因素**：怎么推动决策。

原文强调：重点看第一、第二部分；第三、第四部分是具体场景的最佳实践。

## 第一部分：思考预期和目标

### 搞清楚预期，想清楚目标

写文档前，最重要的是充分理解写文档的背景信息和目标。动笔前要确认：

- 为什么要写？
- 在什么情况下写？
- 以什么视角写？
- 这个文档到底要解决什么问题？

### 接收信息和实际诉求可能有偏差

自上而下传递的信息经常是碎片化的。如果没搞清楚对方真正想要什么，就容易被表面需求带着跑。

原文给了三个例子：

- **用户画像分析**：表面需求是分析用户画像，真实预期可能是看团队是否对新业务有清晰定位、定性认知和后续规划。
- **NPS 报告**：表面内容是满意度数据，真实问题可能是怎样量化业务对用户的价值，以及是否知道当前问题并有解决方案。
- **更快的马**：用户说想要一匹更快的马，真实诉求是用更短时间到达目的地。不能只听表面需求，要追问背后的问题。

写作时要识别这种偏差：接收到的词，不一定就是文档真正要回答的问题。

### 搞清楚预期的方法

原文给出三种动作：

- **多想**：多想两次为什么和怎么做。
- **多问**：信息量不够、过程想不清楚时，要去问。
- **验证**：有了一定想法后，可以先形成框架性文档，确认是否和预期契合。

### 目标决定主线

文档是一种沟通方式，沟通的核心是达成目标。有了目标，文档才有核心主线。

写作前要想清楚：希望对方看完文档后导向什么决策？

原文举例：

- 希望对方投入更多资源，因为这件事重要。
- 希望对方砍掉某块业务，因为已经证明没价值。
- 希望对方找某个人协助，因为只有这样才能解决当前问题。

如果没有目标，只做现状阐述和信息罗列，不同读者会形成分散结论，甚至导向错误决策。

## 第二部分：信息组织的关键要素

### 视角：需求视角和供给视角

从需求视角组织文档。先想清楚：

- 看文档的是什么角色？
- 不同角色关注什么？
- 不同角色对信息密度的要求是什么？

不要只从“我有什么信息”出发，而要从“读者为什么要看、需要什么判断”出发。

### 不要写标题，要写观点

标题不要只是罗列主题，而要表达观点。

检验方式：只读目录，是否能了解文档主要观点？

原文要求：

- 标题要能表达所有观点。
- 观点展示在段头，便于读者获取信息。
- 如果读者看完观点已经清楚，可以结束阅读。
- 如果读者存疑，再继续下钻，看论据是否足够支撑观点和结论。

这对应金字塔原则：结论先行，上层概括下层。

### 框架：做逻辑拆解，把事情讲清楚

写文档框架，本质是在做逻辑拆解。要选择能讲清楚问题的拆解维度。

原文给出两类框架：

- **通用逻辑**：现状、问题、to do。常用于把一件事拆清楚。
- **业务逻辑**：拆解业务增长公式。例如直播业务可拆为 `DAU × 渗透率 × 付费率 × 付费 ARPU`。

用业务逻辑拆解后，要围绕核心指标介绍进展、问题、归因和后续 to do。所有事情都应该和核心指标相关。

原文还按业务阶段给出示例：

- **启动期**：探索各场景最优体验和策略，优化曝光点击，挑选主播。重点关注渗透和转化。
- **增长期**：场景体验稳定，加强渗透和转化，增大开播量。重点促进模式成熟和付费率渗透。
- **成熟期**：场景、付费率稳定，持续探索。重点关注 ARPU 和生态泛化，横向拓展规模。

### 判断：数据和用研有偏差

不要只相信数据，要关注偏差。

原文提醒：

- 不同统计方法会有偏差。
- 缺少其他因素的考量会有偏差。
- 对同一数据的不同描述，也会影响人的判断框架。

用研也会有偏差。用户说的、用户以为自己说的、别人听到的，可能都不一样。要结合用户行为分析，而不是只听用户怎么说。

写作时要先有业务逻辑和观点，再组织数据和用研信息，整理出支撑观点的论据。不要先堆数据和用研，再从中找信息拿来用。

原文总结：不要围绕数据和用研，而是围绕观点。

### 目标：决策因素和推动决策

写文档最核心的目标是推动决策。

写作过程中要做到：

- 全程扣题。
- 明确决策点。
- 形成决策线索。
- 给出明确结论，推动决策。

原文列了两个常见 bad case：

- **找错决策角色**：这事该找谁？谁能做决策？谁来投入资源？相关方是否在场？
- **没有可选项和决策点**：只有一个方案，没有决策要素，读者不知道怎么判断。

### 表达：文档操作 tips

#### 结论要定量，不要定性

原文例子：

- 说法 1：方案 A 和 B 比较，A 方案显著好。
- 说法 2：方案 A 和 B 比较，A 方案在 xx 数据上提升 1%。

优先使用第二种。定量表达更能支持判断。

#### 信息压缩，不要废话

原文引用金字塔原则和麦肯锡 30 秒电梯理论，强调：

- 结论先行。
- 聚焦重点。
- 最简短高效地沟通。

原文的提醒：如果不觉得自己的工作比政府工作报告还复杂，很多文档应该能用 500 字说清楚。

#### 所有模板都只是参考

可以使用达成共识的逻辑模板，但不要完全照搬。要有自己对业务的思考和判断。

#### 尽量不使用专业术语和缩写

减少跨专业词汇、英文缩写、模糊抽象话语。让读者能直接理解。

## 第三部分：双周报怎么写

### 预期和目标

继续用灵魂三问：

- 为什么要做这件事？
- 谁想看？
- 为什么要看？

双周报的目标：

- 对业务负责人：收集业务信息，了解各方向进展和问题，并在合适时间提供资源，促进业务推进。
- 对各方向业务线 leader：梳理近期重要进展和问题，沉淀、总结、复盘，也了解其他方向的重要事项，促进协同。

### 框架模板：基于业务逻辑整合信息

原文给出两个核心动作：

- **提取核心指标**：明确该业务方向的核心指标，看数据变化和趋势，解释并归因。
- **拆解业务模块**：
  - 模块进展同步：确认和核心指标相关的业务模块，看模块核心数据，关注变化和进展。
  - 关键项目同步：可以同步协同确认、资源瓶颈、决策要素对齐、调研结论。

### 双周报 tips

信息来源：

- 周报。
- 日常工作。
- 双月 OKR。

写作节奏：

- 每个双周开始，先思考各业务模块的核心事项。
- 日常工作中不断验证和修订观点，用具体信息补充论据。
- 双周会前检验是否传达清楚观点，论据是否准确。

产出过程：思考 → 提炼 → 补充 → 检验。

不是所有信息都要同步。原文明确不需要讲：

- 没上线的。
- 进展顺利、没什么问题的。
- 没问题点和决策点、只是拿来知会的。

要突出决策点或问题点的信息。

## 第四部分：业务关键问题材料怎么写

### 预期和目标

关键问题材料的目标是：对齐关键问题认知，做好沉淀并指导后续工作和合作。

原文要求最终形成：

- 阶段共识。
- 具体操作规范或最佳实践。

材料形成过程：有观点和论据 → 通过补充和修订达成共识 → 以共识为指导原则，补充最佳实践和指导建议。

写作过程：分析问题 → 确认框架 → 论据补充 → 确认观点。

### 分析问题

写作前，思考和交流很重要。要和提问者及问题相关方沟通：

- 谁提的？为什么提？
- 谁和问题相关？
- 谁能协助解答问题？
- 他们的诉求是什么？
- 想要什么答案？

不要局限于文字表面。分析问题要考虑多立场，站在不同角度提炼观点。

### 确认框架

先形成故事线，也就是文档提纲。

原文分两种情况：

- 观点明确：直接列提纲，形成 500 字故事线。
- 观点不明确：先确定大概方向，深入拓展，梳理几个相关立意，通过思考、阅读材料、交流，确定核心主题和观点。

故事线的形成方式：

1. 收集信息和讨论。
2. 形成初步观点和框架。
3. 基于观点演绎，看是否有论据支撑，是否适用所有情况。
4. 遇到问题就回到收集信息和讨论。
5. 重新调整和修正。
6. 最终抽象总结，形成完整信息。

整体是归纳和演绎的过程：先抽象形成观点，再演绎看是否适用。

### 论据补充

用论据解释说明核心观点。

原文要求：

- 文章结构谨记金字塔原则。
- 内容组织从现有数据和历史信息中找论据。
- 有观点和解释说明后，一定还要有最佳实践。

### 确认观点

整体 review 和纠偏时检查：

- 是否有整体核心观点？
- 是否有效表达完整观点？
- 分论点是否清晰？
- 每个分论点的论证是否合理、明确，有足够数据或论据支持？
- 分论点之间是否有逻辑关系（总分、递进、并列）？
- 分论点是否支撑核心观点？
- 全篇是否能清晰解释前面的概论总述？

### 最终产出材料

原文用敏捷宣言作为对标：敏捷宣言 → 四大价值 → 十二大原则 → 各原则的最佳实践。

这类材料要层层递进解释：

- 顶层共识。
- 价值或原则。
- 各原则的最佳实践。

## 使用这个 skill 时的检查清单

- [ ] 写前回答了：为什么做、谁想看、为什么看。
- [ ] 区分了表面需求和实际诉求。
- [ ] 明确了文档目标，以及希望读者看完后导向什么决策。
- [ ] 从读者需求视角组织信息，而不是从作者供给视角罗列信息。
- [ ] 标题表达观点，而不是只写主题。
- [ ] 段头先给观点，后面用论据支撑。
- [ ] 框架能讲清问题，且和核心指标或核心问题相关。
- [ ] 数据和用研没有被直接当成结论，已经考虑偏差。
- [ ] 有明确决策点、决策角色、可选项或推动动作。
- [ ] 结论尽量定量，不只定性。
- [ ] 删除了无决策点、无问题点、只用于知会的信息。
- [ ] 模板只是参考，最终结构服务于这次具体问题。
